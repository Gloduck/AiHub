# 通用规范
+ 在整个开发过程中，会涉及到代码编写、功能测试、Review流程。如果用户的改动是个较为大的功能（改动）话，应该开启三个子任务来分别处理，然后主代理和用户沟通需求设计以及协调。如果功能简单，则可以直接有主代理完成整个开发流程（即使已经有了对应的子任务）。其中开发和Review子任务需要的思考等级需要调高，测试可以使用低的思考等级（甚至使用低级的模型）

# 代码编写规范

+ 只修改约定范围内的内容；需要扩大范围时，先说明原因并与用户确认。
+ 结合现有代码判断需求是否合理。若改法与现有结构冲突、需要大量兼容逻辑或实现过于曲折，先说明取舍，与用户讨论更直接的方案。
+ 遇到不确定的问题，先查文档或核对现有实现，不凭猜测编写代码，如果没有相应的文档或者资料，可以向用户确认。
+ 根据实际风险设计参数校验和兜底逻辑，避免过度防御导致代码难以维护。
+ 使用用户当前的语言写注释。对关键逻辑，简明说明意图；对特殊场景的补丁，注明为什么需要例外处理，方便用户后面朔源。
+ 工具方法，通用的方法可以优先封装（复用）工具类，避免同一个方法多次引用，并且根据具体功能大类来命名工具类。
+ 对于拿不准的代码，可以优先向用户明确其用途，不要假定这个代码是废弃的代码，有可能用户是用来处理某个特殊场景的。
+ 代码的改动可能会涉及老数据的兼容，遇到这种需要先和用户明确是否需要兼容，怎么兼容，不要默认就以为需要/不需要兼容。
+ 代码编写保持最小改动原则，能有方式最小改动实现的就不要扩大改动范围。

## Java代码编写规范

+ 对象判断优先使用Objects.equals判断。
+ 在使用Map的时候，如果顺序不是必要的话，优先使用HashMap。
+ 在构建实体类的时候，非必要情况，避免给默认值。默认值应该通过构造方法或者外部构造。

## 脚本编写规范

+ 非指明的情况下，脚本优先使用shell（需要兼容Git Bash）、powershell、cmd实现，以便操作系统能够直接运行。如果涉及到实现复杂、跨平台实现（Git Bash跨平台可以支持的话不算）、维护成本过高的情况下，可以尝试使用Python、Node等语言来实现脚本。
+ 脚本尽可能写法按照能同时兼容Linux、Windows两个系统的写法来编写（非强制）。如果需要拆分成不同的入口（如：`xxx.sh`、`xxx.bat`），需要保证脚本名称、参数名、参数含义、默认行为、退出语义应尽量一致。平台差异无法完全消除时，应在 `--help` 中明确说明差异。
+ 所有的脚本必须实现`-h`/`--help`命令，示意脚本的功能，参数列表等，使用英文编写，参数列表简单说明，不需要体现具体实现逻辑。
+ 脚本尽可能保持能够单文件运行，以方便脚本能够复制到其他的及其上使用。复杂的脚本可以不用保持单文件。
+ 脚本需要保持在任意目录执行的能力，用户可以在其他的路径下运行这个脚本，而非要先进入脚本所在路径再执行对应脚本。
+ 脚本名应直接表达动作与对象，避免使用无语义缩写，并且以下划线命名法来命名。
+ 如果脚本是风险脚本，需要支持`--dry-run`，以便用户能提前预估风险。
+ 对于复杂的脚本、脚本子功能过于独立，可以使用子命令来实现，脚本的参数列表必须使用对应的参数名来指定。避免通过参数的顺序来指定。

## 前端编写规范

+ 如果是以HTML的形式编写前端代码的话，依赖的外部js、css在用户没有特殊说明的情况下优先使用外链引入（尽量选择当前网络环境速度快的源），并且需要尽量支持单机打开就能运行。

# Review规范

+ 结合现有代码分析问题根因，优先提出能解决同类问题的修法，避免逐个特例打补丁。
+ 发现约定范围之外的问题或影响时，向用户说明并讨论是否处理，不直接修改。
+ Review主要针对常见的场景进行分析，不要为了很特殊（极小发生）的场景专门指出修改。

# 测试规范

+ 单元测试需要根据当前项目而定，如果当前项目没有单元测试，没必要单独引入单元测试。
+ 有些单元测试可能依赖依赖于特定的操作系统，如果当前环境无法执行对应操作系统的测试，可以由AI直接给用户对应操作系统的测试命令，然后由用户直接复制命令在对应的操作系统里面执行，以达到测试的效果（如果存在对应操作系统的单元测试，则仍要补充）。
+ 有些测试可能会依赖三方工具、特定的隔离环境，AI可以适量安装必要的工具（最小化）到临时路径（如果有必要安装到非临时路径，需要找用户确认，不能静默安装），然后向用户指明使用的工具，在整个任务完成过后向用户询问是否需要清理这些临时的环境。
+ 浏览器依赖的测试任务，如果当前AGENT没有特定的浏览器工具，可以尝试使用：playwright-cli来进行浏览器任务的测试。playwright-cli的浏览器内核，在用户没有明确指明的时候，优先使用当前电脑已有的浏览器内核（以前playwright-cli已经安装过的内核），不要每次执行一个任务都安装一个内核。并且执行的时候playwright-cli执行的时候会生成很多中间文件，这些文件在任务完成过后需要向用户询问是否需要清理这些文件。

# Git提交规范

+ Git commit提交使用标准格式：类型(范围/功能/Bug号): 简短描述，类型根据当前改动的类型来定义为：feat/fix/docs/refactor/test/perf/chore。
+ Git 提交每次最好针对单个功能进行提交，避免将一大堆功能混在一个提交里面。对于大功能的改动可以分段提交。
